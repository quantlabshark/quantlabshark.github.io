订单簿与随机模型

46 · 订单簿重建与成交机制

按订单事件恢复价格时间队列，用逐笔现金流、数量守恒和消息完整性判断成交。

订单簿重建按行情消息逐步更新价格、数量和队列。新增、撤单与成交作用于不同对象，保持消息顺序和数量一致是计算后续特征的基础。

报价、成交价和订单是三类记录

买一99.98元表示当前最高的可见买入报价，卖一100.00元表示最低的可见卖出报价，中间价为99.99元。成交价来自某笔实际撮合，可能在买一、卖一或更深价位。没有成交时，新增或撤单也会改变报价。

订单簿是“仍未成交、尚未撤销的订单”的集合。重建订单簿就是按事件顺序更新这个集合。必须知道每条消息的数量是增减量还是更新后的总量：把“新总量80”当作“再增加80”，即使价格正确，深度也会迅速偏离真实状态。

同一价格内还存在先后顺序

本课采用价格优先、同价时间优先的连续撮合模型。卖价越低越先成交；同价订单先到先成交。设卖盘如下：

订单 卖价（元） 数量（股） 同价位置
A 100.00 60 最前
B 100.00 40 A之后
C 100.01 150 下一价位

买入180股的主动订单依次消耗A的60、B的40、C的80，均价为

pˉ=60×100+40×100+80×100.01180=100.004444….\bar p=\frac{60\times100+40\times100+80\times100.01}{180}=100.004444\ldots.pˉ​=18060×100+40×100+80×100.01​=100.004444….

这笔买入多付的0.80元来自最后80股的每股0.01元抬价。成交后卖一变为100.01、数量70。买一若未变化，中间价变为99.995。成交均价100.00444、最后成交价100.01、新中间价99.995分别回答不同问题。

逐价位数据与逐订单数据

逐价位数据只告诉我们100.00元共有100股。逐订单数据还告诉我们其中有A、B两张订单及顺序。两者都可以描述总深度，只有后者在消息协议提供足够信息时，才能恢复具体排队位置。订单编号用于关联生命周期，不等于投资者身份。

若自己的买单前有200股，之后同价新增100股通常排到后面，自己的前方数量仍为200。随后出现80股主动卖出，前方降为120。再发生50股撤单，只有撤在自己前面才继续减少前方数量。仅看到价位总量减少50，不能确定这50股原来排在哪里。

把消息转换成状态转移

维护 订单编号→方向、价格、剩余数量 的字典，再维护 价位→有序订单队列。新增使数量增加，部分撤单和成交使数量减少，归零时移除。改价在本课模型中先撤旧单再插入新单，因而重新排队。不同市场的数量修改与优先级规则应单独进入适配层。

事件 数量变化 价格变化的可能性
新增限价单 增加可见深度 新报价改善最优价时变化
撤销订单 减少未成交量 最优档清空时变化
主动成交 消耗被动订单 最优档耗尽时变化
快照重置 用完整状态替换本地状态 重新确定所有档位

下列代码只处理卖盘，价格以“分”为整数保存。deque 是从队首取订单的双端队列，min 保证每次成交不超过主动需求与被动剩余量。

Python26 行
from collections import deque
ask = {10000: deque([['A', 60], ['B', 40]]),
       10001: deque([['C', 150]])}
def buy_market(quantity):
    fills = []
    for price in sorted(list(ask)):
        queue = ask[price]
        while queue and quantity:
            oid, available = queue[0]
            size = min(quantity, available)
            fills.append((oid, price, size))
            quantity -= size
            queue[0][1] -= size
            if queue[0][1] == 0:
                queue.popleft()
        if not queue:
            del ask[price]
        if not quantity:
            break
    return fills, quantity
fills, unfilled = buy_market(180)
cost = sum(price*size for _, price, size in fills)
print(fills, '未成交', unfilled)
print('成交均价', cost/180/100)
assert fills == [('A', 10000, 60), ('B', 10000, 40), ('C', 10001, 80)]
assert ask[10001][0][1] == 70

输出的三笔成交依次为A60、B40、C80，未成交量为0。断言检查了成交顺序和C剩余70股。若需求改为300股，可见250股耗尽后应留下50股未成交。不能把未知深度自动填在最后一个价格上。真实订单是否撤回剩余部分，要由有效期和价格保护条件决定。

数量守恒与消息完整性

对每张被动订单，应始终满足“初始量＋有效增量＝累计成交＋累计撤销＋剩余量”。对每个价位，汇总数量应等于该价位全部订单剩余量之和。重复新增、负数剩余量、撤销不存在的编号，通常说明协议解释、消息排序或丢包处理存在问题。

一个撮合事件可能拆成“成交摘要”和“深度更新”两种消息。若两者都被当作独立减量，订单会被扣两次。同一完整事件也可能跨多个网络包：先收到了成交摘要，并不代表订单簿已完成更新。生成信号的时点应是所需原子事件已经完整处理之后。

事件序号从100跳到103时，应标记缺失并恢复快照/增量，而不是默认101和102没有改变盘口。快照有自己的序号基准，恢复时要避免把已包含在快照中的旧增量再应用一遍。

将重建结果用于回测

用事件发生时间研究市场顺序，用本地接收时间判断策略何时知道这些信息。订单发送后还要经过传输、网关确认和排队，不能把确认后的最优位置倒填到发送时刻。隐藏数量、冰山补量、交易更正和集合竞价应有各自的状态规则。

最低价触及买入限价，只说明市场曾在那个价格附近成交。要判断自己的订单能否成交，还需到达时间、排在前面的量、后续主动流量，以及撤单位置。盘口重建给出的正是这些成交模型的输入。

逐笔回放订单与成交

设订单D在10.00元挂买100股。依次收到部分成交30股、撤销20股、成交25股。每一步的剩余量如下。

事件后 累计成交 累计撤销 剩余量
新增 0 0 100
成交30 30 0 70
撤销20 30 20 50
再成交25 55 20 25

每行都满足100等于三项之和。若成交摘要的30股已经扣过，再收到深度更新后又扣一次，就会在第二行变成剩余40，守恒立刻失败。实际协议可能只给总量而不给撤销差额，此时应由更新前后状态计算变化，再关联相关事件。

再看策略到达时点：10:00:00.000观察买一前方200股，0.010秒后发单，0.020秒后确认。期间若新增50股且按时间排到自己之前，确认时前方可能已250。反之期间成交80股则前方可能减少。用观察时200固定整个排队过程，会漏掉发送期间的竞争。

买卖方向怎样对应队列

主动买单消耗卖盘，被动卖单获得成交。主动卖单消耗买盘，被动买单获得成交。某些数据把方向字段定义为主动方，另一些记录被动订单方向，读入前应先转换到统一含义。一个标记为“buy”的事件究竟增加买方深度还是消耗卖方深度，不能只看字段英文猜测。

将十条人工构造事件逐条画出盘口，核对新增、撤销、跨档成交和改价，比一开始对百万条消息只看最终总量更容易发现方向错误。确认小例后，再检查完整交易日的序号连续性与收盘快照。

练习

1. 先撤A20股，再买入80股。卖一价和量如何变化？

查看解答

A剩40，B仍40，主动买入恰好消耗100.00元的80股。新的卖一是100.01元、150股，成交均价100.00元。

2. 一张100股订单累计成交35、撤销20，当前剩余50。哪项不满足守恒？

查看解答

35＋20＋50＝105，比初始量多5。若没有有效增量消息，正确剩余应为45。应回查这张订单的消息序列，不能直接把50改成45后忽略数据缺口。
