1. 八球称重

题目

8 颗外观相同的球中恰有一颗较重，其余质量相同。使用无砝码天平，保证找出重球最少需要称几次？给出方案和最优性理由。

考点：信息下界；三分决策；最坏分支。

查看分析与解答

必要知识

天平每次有三种结果，因此深度 d 的决策树最多区分 3ᵈ 个候选状态。已知唯一异常偏重时，每颗球对应一个候选；若轻重未知，状态数会不同。

分析思路

先用结果数量证明一次不够，再把八个候选分成三组，每组不超过三，使第二次称量能够区分任一剩余分支。

解答步骤

两次最多九种结果只是容量条件，还需给出每个分支都合法的称法。分成 3、3、2 恰好使第一次三个结果分别指向三个大小不超过三的候选集。

天平一次有左重、右重和平衡三种结果，只能区分至多 3 个候选，不能确定 8 颗中的重球。因此至少需要两次；两次最多有 32=93^2=932=9 种结果，信息数量上允许区分 8 个候选。

将球分成 3、3、2 三组，第一次称前两组。

  • 若平衡，重球在剩余两颗中，第二次将它们各放一边，较重者即答案。
  • 若一边重，重球在该边的三颗中。第二次取其中两颗各放一边：不平衡时取重者；平衡时取未上秤的第三颗。

每个分支都在两次内结束，故最少为 2 次。这里已知异常球偏重；若偏重或偏轻均可能，候选状态数和判断方法都会改变。

将球编号 A 至 H，先称 ABC 对 DEF。平衡则比较 G、H；左重则比较 A、B，平衡是 C；右重则比较 D、E，平衡是 F。可以给每颗球列两次结果路径：例如 C 对应左重、平衡，H 对应平衡、右重。八条路径互不相同，保证没有遗漏。

同类问题

保证最少次数的问题，应同时给下界与达到下界的决策树。只说 3²≥8 还不能证明具体称重限制下能够实现。

2. TCP 长连接

题目

客户端与服务器通过 TCP 持续传输行情。如何复用连接、发现失效并在重连后恢复消息处理？

考点：字节流；心跳；消息序号与幂等。

查看分析与解答

必要知识

TCP 提供有序字节流，不提供应用消息边界。一次发送可能分成多次接收，多次发送也可能合在一次接收中。连接存活、字节送达、业务已处理是三个不同层次。

分析思路

按消息封装、故障检测、重连恢复三层设计。先能正确拆包，再判断何时认为连接失效，最后用业务序号与状态恢复处理丢失和重复。

解答步骤

可在每条消息前放固定长度的消息长度字段。接收端先积累完整头部，再等待指定长度正文，处理后继续解析缓冲区中的下一条。只读到半条时应等待后续字节，不能将其当作完整行情。

连接建立后可以持续收发多条消息，不必为每条行情重新连接。应用层需要规定消息边界，例如长度字段，避免把一次接收调用误认为一条消息。

发现失效可结合读写超时、TCP keepalive 和应用层心跳。心跳间隔应小于中间网络设备的空闲回收时间，并容许短暂抖动。若连续超时，关闭旧连接并按有上限的退避策略重连。连接仍显示已建立，并不说明远端应用仍能处理请求。

恢复时利用业务序号检测重复和缺口。例如已处理序号 100，重连收到 100、101，应忽略已处理的重复记录，再继续 101。若直接收到 103，则请求补发 101、102 或获取状态快照。需要确认的业务还应区分“写入本机发送缓冲区”与“对方应用已处理”。

因此长连接设计包含连接复用、故障检测和消息恢复三部分。仅周期性发送一个字节，不能解决漏消息或重复处理问题。

若最后持久化处理序号为 100，重连从 101 请求重放。收到重复 100 时按消息标识去重；收到 103 则先修补 101、102，或获取带序号的一致快照后再接增量。确认应在约定的处理或持久化阶段发送；仅 send 返回成功并不说明远端业务完成。退避加入随机扰动可以减少大量客户端同时重连的压力。

同类问题

长连接可靠性应由应用协议补齐消息边界、确认语义和恢复位置。心跳只帮助发现失效，不自动提供业务上的恰好一次处理。

3. I/O 占用

题目

Linux 上一个行情处理进程延迟升高，怀疑磁盘 I/O 是瓶颈。应观察哪些指标，怎样区分设备繁忙、进程等待和缓存影响？

考点：I/O 延迟；吞吐与队列；缓存。

查看分析与解答

必要知识

吞吐是单位时间传输字节数，IOPS 是请求数，延迟是请求等待与服务耗时，队列深度是尚未完成的请求数量。高吞吐与低延迟并非同一目标，小同步写可能在吞吐很低时仍造成长等待。

分析思路

先定位应用哪个阶段变慢，再把相同时间窗口的进程与设备指标对齐。结合请求大小、同步方式和缓存命中解释现象，而不是凭一个利用率数值下结论。

解答步骤

例如每条行情都写 100 字节并立即同步落盘，即使每秒只有一万字节，也可能因频繁等待持久化造成高延迟。将一百条组成批次可能降低同步次数，但会增加批次等待，需要同时评价吞吐与尾延迟。

先确认延迟发生在哪一阶段：数据读取、计算还是落盘。查看进程 CPU 使用率和 I/O 等待，同时观察设备吞吐、请求数、平均等待时间与队列深度。

可用 iostat 查看设备指标，用 pidstat 或 iotop 定位读写较多的进程。若吞吐不高但每次写入都等待，可能是大量小同步写。若队列和等待一起上升，可能是设备服务能力不足或其他进程竞争。单独看到高利用率，不能区分这些情况。

还要区分页缓存与物理设备访问：首次读取文件可能访问磁盘，再次读取可能命中缓存；写调用返回也可能只是进入缓存，后续同步落盘才产生延迟。对照应用记录的调用耗时与设备指标，才能定位。

依据证据选择批量写入、减少重复读取、调整缓存或存储布局。优化后在相同负载下比较尾部延迟与吞吐，不能只比较一次短时间平均值。

诊断可按“应用写入耗时上升—对应进程写请求增加—设备等待与队列增加”建立证据链。若应用慢但设备空闲，应转查锁等待、网络或 CPU；若首次读慢而再次快，缓存可能解释差异。设备并行度不同，高利用率不必然等于已达到可用吞吐上限。

同类问题

性能排查先测量端到端延迟分解，再关联资源指标。优化前后采用相同负载、持续时间与缓存条件，并记录分位延迟，避免用均值掩盖偶发停顿。

4. 结束进程与信号

题目

Linux 进程需要停止时，SIGTERM、SIGKILL 和 kill -0 分别有什么作用？说明一个能保留业务状态的退出流程。

考点：信号；优雅退出；恢复检查点。

查看分析与解答

必要知识

SIGTERM 是可被处理的终止请求，SIGKILL 强制终止且不能捕获、阻塞或忽略。kill -0 不实际发送信号，只进行目标存在性与权限检查。进程存在也不代表正常工作，僵尸进程等状态需进一步区分。

分析思路

先确认目标身份，再请求程序按业务顺序退出，等待并观察；只有超时且明确可接受恢复后果时才考虑强制终止。退出协议与下次启动的恢复协议应配套。

解答步骤

行情落盘服务可按“停止接收新批次—排空已接受队列—写入并同步检查点—关闭文件与连接—退出”执行。信号处理通常只设置退出标记，由主循环完成复杂操作，避免在底层异步信号处理器中调用不安全函数。

先核对进程号、启动时间和所属任务，避免终止同名但无关的进程。通常先发送 SIGTERM，请求程序退出；程序可处理该信号，停止接收新任务，再完成或回滚正在进行的操作，保存检查点并关闭资源。

主进程应在限定时间内等待退出，同时查看日志和子进程状态。若无法退出，再判断是否适合使用 SIGKILL。SIGKILL 不能被捕获、阻塞或忽略，程序没有机会执行清理。未完成的业务写入可能需要恢复机制处理。

kill -0 不发送终止信号，用于检查目标进程是否存在及是否具有发信号权限。检查成功与随后操作之间，进程状态仍可能变化。

例如行情写入服务可先停读新消息，等待已接收批次写入并保存最后序号，然后关闭文件。下次启动从该序号恢复，避免因退出造成重复或缺失。

若最后数据批次已落盘而序号检查点未更新，下次可能重复处理；若先更新检查点而数据未落盘，下次可能漏处理。因此数据与处理位置应采用事务、原子替换或可重放的幂等协议保持一致。SIGKILL 无法补做这些步骤，恢复必须依靠事先设计。

同类问题

停止进程不仅是发出一个信号，还包括确认目标、排空工作、保存一致状态与验证退出。kill -0 的检查与后续操作之间存在竞态，不能当成持久保证。

5. mmap 与共享内存

题目

说明文件映射 mmap、共享映射和私有映射的区别。两个进程通过共享内存传递行情时，还需处理哪些问题？

考点：虚拟内存；共享与私有映射；同步。

查看分析与解答

必要知识

虚拟地址是每个进程自己的地址视图，映射把一段地址连接到底层文件或内存页。MAP_SHARED 的修改可被其他共享同一区域的进程观察；MAP_PRIVATE 通常通过写时复制保持私有修改，不回写为共享更新。

分析思路

先区分地址访问机制、跨进程可见性与持久化，再设计生产者发布消息的同步顺序。共享内存解决传输位置，不自动解决读到完整记录的问题。

解答步骤

生产者若先写“消息长度为 100”，再慢慢填正文，消费者可能看到新长度却读到旧正文。正确协议应先完成内容，再以适当同步发布可读状态；消费者先获得发布状态，再读取内容。使用进程共享锁可以直接建立这个顺序。

mmap 将文件或匿名内存区域映射到进程的虚拟地址，程序可通过内存读写访问它。映射建立不代表全部页已进入物理内存；首次访问可能触发缺页，文件映射也可能产生磁盘访问。

共享映射让多个进程访问同一底层数据，适合传递行情队列。私有映射的修改通常通过写时复制形成进程自己的副本，不按共享写入方式传播给其他映射。共享文件映射的可见性与数据持久化也需要区分，必要时还要按约定同步至文件。

共享内存省去了一些数据复制，但没有自动给出一致的读写顺序。生产者可能先改长度再写数据，消费者因而读到未写完的记录；可用进程共享锁、信号量，或经过论证的原子序号协议，保证发布与读取的顺序。

还需约定创建和删除责任、结构版本、缓冲区满时的处理、崩溃恢复与读写权限。存入跨进程数据结构的应是偏移量或索引，不能直接保存仅在某进程有效的普通指针。

两个进程映射同一文件的虚拟起始地址可能不同，因此共享结构中记录“正文偏移 64”可以由各自基址加偏移访问，记录某个进程指针则无效。还要定义写指针追上读指针时阻塞、丢弃还是覆盖，以及生产者崩溃后如何识别未完成消息。共享可见不等于已经持久化到磁盘，文件同步是另一个问题。

同类问题

共享内存方案至少需要布局、同步、容量和生命周期四部分。任何无锁协议都应明确原子操作和内存顺序，不能仅凭“两个进程看到同一块内存”推断一致性。

6. 静态库与动态库

题目

比较静态链接与动态链接在构建、部署、升级和运行时依赖方面的区别。若程序启动时提示找不到共享库，应按什么顺序检查？

考点：构建与装载；符号；ABI。

查看分析与解答

必要知识

编译把源代码变成目标文件，链接解决目标文件间的符号引用，装载则把程序及动态依赖放入运行进程。ABI 规定二进制接口，包括调用约定、名称、数据布局等；它与源码层面的函数名相同不是一回事。

分析思路

先按生命周期比较静态与动态链接，再把启动错误分成“找不到文件”“架构不匹配”“缺少符号”等类别，沿对应环节检查。

解答步骤

静态链接通常只把需要的库对象合入程序；动态链接则在程序中保留依赖及符号关系，由装载器寻找兼容库。若 A 依赖 B、B 又依赖 C，即使 B 存在，缺少 C 仍会使 A 启动失败。

静态链接把库中需要的目标代码合入可执行文件。部署时相关外部库依赖较少，但不同程序通常各带一份代码，库升级后通常需要重新链接和发布程序。

动态链接保留对共享库的引用，由装载器或运行时解析。多个程序可以使用相同库文件，升级有时不必重建所有程序。但库名称、搜索路径、体系结构和 ABI 必须兼容。ABI 涉及函数调用约定、符号和数据结构布局，文件存在并不代表可用。

出现找不到库时，先查看程序记录的依赖名称，再确认文件是否安装、位数和架构是否一致，随后检查搜索路径及间接依赖。若文件能够找到却缺少符号，则重点核对版本与 ABI，而不是不断添加路径。

性能差异取决于装载开销、调用方式和编译优化。选择时应围绕部署方式和升级要求衡量，不宜仅凭“静态”或“动态”判断速度。

排查顺序可以是查看依赖名称与架构、确认库和间接依赖是否安装、核对加载器搜索路径，最后检查所需符号及版本。出现 undefined symbol 时，继续添加更多目录可能加载错误版本，应该对照构建时与运行时接口。静态链接也未必意味着完全没有系统运行时依赖，应查看实际产物。

同类问题

构建成功不保证部署可运行。根据错误发生在链接还是装载阶段选择检查对象，能避免把版本兼容问题误当成单纯路径问题。

7. 量取 4 升水

题目

有容量分别为 5 升和 7 升的无刻度容器，可从水源装满任一容器、倒空任一容器，或向另一容器倾倒至一方空或另一方满。如何量出 4 升？

考点：状态图；合法操作；容量约束。

查看分析与解答

必要知识

用两容器当前水量作为状态，合法操作只有装满、倒空和倒至一方空或另一方满。倾倒量等于 min(源容器水量,目标剩余容量)，因此每一步的结果可精确计算。

分析思路

利用七升倒入五升后剩两升，先把这两升转到小容器。再用满七升补足小容器所缺三升，便留下四升。

解答步骤

第一次余两升来自 7−5。把两升留在五升容器后，它还缺 5−2=3 升；从满七升倒出这三升，剩余 7−3=4 升。这是操作序列背后的数量关系。

用 (a,b)(a,b)(a,b) 表示 5 升容器和 7 升容器中的水量，初始为 (0,0)(0,0)(0,0)。

  1. 装满 7 升容器：(0,7)(0,7)(0,7)。
  2. 向 5 升容器倒至满：(5,2)(5,2)(5,2)。
  3. 倒空 5 升容器：(0,2)(0,2)(0,2)。
  4. 将剩余 2 升倒入 5 升容器：(2,0)(2,0)(2,0)。
  5. 再装满 7 升容器：(2,7)(2,7)(2,7)。
  6. 5 升容器还差 3 升，补满后为 (5,4)(5,4)(5,4)。

此时 7 升容器中剩 4 升。逐步记录状态可以避免只凭口述漏掉容量条件。一般整数容量问题可把所有状态与允许操作构成图，用广度优先搜索求最少操作数。

如果要求最少操作，可用广度优先搜索，从 (0,0) 开始生成六类操作，记录首次访问的状态及前驱，找到任一分量为四后回溯路径。状态总数至多 (5+1)(7+1)=48，重复状态不再扩展。一般容量 a、b 的整数问题，目标量还受 gcd(a,b) 的整除约束。

同类问题

容器题先定义状态和每个动作的精确转移。手工方案证明可行，最少步数则需要下界或搜索层数证明，不能把一个方案直接称为最优。

8. 口算

题目

不用计算器计算 98×88，并给出另一种方式核对结果。

考点：分配律；基准数；独立核算。

查看分析与解答

必要知识

乘法分配律 a(b+c)=ab+ac 允许把难算的数改写成接近整十或整百的数。核对时换一种分解方向，可降低重复同一算术错误的机会。

分析思路

98 接近 100，所以先算容易的 100×88，再减去多算的 2×88。最后按 88=80+8 分解做独立核对。

解答步骤

先估计结果应略小于 100×88=8800，且末位应为 8×8 的个位 4。精确运算中 2×88=176，8800−176 先减 100 得 8700，再减 76 得 8624。

将 98 写成接近的整百数： 98×88=(100−2)×88=8800−176=8624.98\times88=(100-2)\times88=8800-176=8624.98×88=(100−2)×88=8800−176=8624. 再用另一方向分拆核对：98×(80+8)=7840+784=862498\times(80+8)=7840+784=862498×(80+8)=7840+784=8624。两种算法均只使用乘法分配律，第一种减少了大数逐位相乘的步骤。

反向核算 98×80=7840、98×8=784，相加为 8624。两次结果一致，并符合小于 8800、末位四的预检。估计只能发现数量级错误，不能替代精确计算。

同类问题

口算优先找接近的整基数，减少复杂乘法；再用估算、末位或不同分解检查。每个检查覆盖不同类型的错误。
